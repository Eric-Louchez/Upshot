# Optimisation — current specification

The optimisation metadata: what it is, what it decides and where it comes from.

Derived from the log; where it disagrees with the log, the log wins (spec/README.md).

**OPT-1** The structure that makes a program's data efficient is provided as **optimisation metadata**, kept
separately from the feature-language program, and optional. It is written in the **optimisation language**, which
also holds configuration such as the assignment of data zones to runtimes (RUN-1) (interpretation: J426533).
Source: L426464, L426531, J426533

**OPT-2** The optimisation metadata decides how the data is physically held (which values are stored and which
recomputed, in memory and/or in a database, layouts and indexes). It changes performance, never results: what a
program computes is defined by the feature language alone, and a program with no metadata still runs correctly
(interpretation: J426465).
Source: L426464, J426465

**OPT-3** For a bidirectional computed value (MODEL-4), the optimisation metadata decides which form, the value or
its sources, is the one that is persisted: the runtime can treat a field other than the declared source as the
authoritative one. The program still declares its sources (MODEL-2).
Source: L426464, L427008

**OPT-4** The optimisation metadata can be written by hand, generated by code from usage metrics, or generated by an
LLM.
Source: L426464

**OPT-5** The feature language never references the optimisation language.
Source: L427008

**OPT-6** One feature-language program can have several sets of optimisation metadata, e.g. one per runtime or per
deployment (interpretation: J427011).
Source: L427008, J427011

**OPT-7** How the parallel computed values of an API's configuration values (API-6) are held, cached, kept or
recomputed every time, is decided by the optimisation layer.
Source: L427098

**OPT-8** The optimiser may, on its own, run actions in parallel when their data dependencies allow it without
breaking atomicity, found by static analysis or by runtime analytics, and may decouple successive transactions by
hot-path optimisation or by predicting values and rolling back a wrong guess; the outcome is always as if the actions
ran one at a time (interpretation: J427529).
Source: L427529, J427529

**OPT-9** Relaxations of atomicity, such as letting an action operate on stale values, change results and so cannot
be made by the optimiser on its own (OPT-2).
Source: L427529
