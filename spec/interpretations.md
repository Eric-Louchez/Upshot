| J426464 | L426464 "the feature language" | Upshot has two parts: the **feature language**, in which a program and its data structures are written, and the **optimisation metadata**, kept apart from the program. | J426467 | L426464 "Some computed values can be bidirectional" | A bidirectional computed value has a two-way path to its sources: its sources determine it and it determines its sources, so either side can be the persisted form and the other derived; writing to it is carried back to its sources. |

| J426551 | L426551 "A, B and C must be equally supported", Context of L426551 | Stated generally, beyond the containers example: for objects of a computed collection that carry source values, the feature language can express each of (A) source values belong to the object's identity and survive the object leaving and re-entering the collection; (B) source values end when their object leaves the collection, so an object re-entering starts from defaults; (C) objects have no identity across recomputations, so every recompute yields fresh objects with defaults. | J426552 | L426551 "specification of each object's identity within the computed collection" | Identity is part of the program's meaning (what an object's source values are depends on it), so it is stated in the feature language, per computed collection: e.g. a key derived from what produced the object (a position, a source element's identity, a tuple of values). | J427008 | L427008 "computed property validation constraints", "An action that invalidates a constraint gets rejected" | A validation constraint is a condition over the data, computed like any computed value (it may use computed values and arbitrary computation functions), that must hold after every action. | J427009 | L427008 "any computed value can be converted … into a source value", "any source value can also be converted to a computed value. | J427010 | L427008 "computed values that aren't two way all the way back to all sources are not writable" | "All the way back to all sources" means the two-way path must reach every source the value is computed from, through any chain of computed values; a computed value that depends on even one source through a one-way step is read-only (to write it, an action first converts it to a source, J427009). |
| J427011 | L427008 "several metadata sets" (Claude's smaller point 3, answered "Yep") | One feature-language program can have several sets of optimisation metadata, e.g. one per runtime or per deployment, each changing performance only (OPT-2). |
| J427076 | L427076 "Functions may contain exception handling where a failed function triggers an exception handling function", answering J427008 | Applies to actions and computation functions alike. The failed action's own changes still never take effect (J427008 stands for those); what the handler does (return a fallback, run another action, record the failure) is its own work and can leave a trace. Without a handler, the failure propagates to the caller. |

| J427099 | L427098 "The user doesn't change. | J427100 | L427098 "metaprogramming … the entire structure/archtecture of the the computed values or even the API itself be computed from other values" | Metaprogramming is part of the feature language: the shape of computed values (which values and collections exist, their structure) and of an API (which values and actions it exposes) can be computed from other values, so that, e.g., the API used in a session depends on the user's role. Since an API's shape can then depend on a configuration value, it is fixed for a session (J427099). |
| J427445 | L427445 "Without migration, migration becomes a built-in metaprogramming-like operation" | "Without migration" is read as "without metaprogramming": where a program does not use metaprogramming (META-1), migration is still available, as a built-in operation of the same kind. |
| J427446 | L427445 "parallel code versions in a single program while migrations are allowed", "keep a snapshot of your whole program at each migration version you want to support", "hot upgrades with no downtime" | A program can hold several versions of itself at once: each supported version is a full snapshot of the program, kept alongside the current one. The old and new versions run in parallel during an upgrade, so the zones of the old version keep serving (their APIs, sessions and actions) while the migration runs and the new version takes over; this is what makes an upgrade hot. When an old version stops being served is not yet specified. |
| J427447 | L427445 "automatic migrations for source data in the new version where the matching value in the old version has the same format/data type/structure. Every other new source value needs the migration transform to give it a value. |
| J427448 | L427445 "The migration operation is treated like a normal action which has its own transaction version" | Like any action (ACT-3, CONS-2), a migration is atomic and is checked against the new version's validation constraints: a migration whose result breaks one is rejected, and the old version keeps running. Its result is one new version of the data, so history before and after it is continuous. |
| J427505 | L427505, L427445 "parallel code versions", "hot upgrades with no downtime", replacing J427446's "old and new versions run in parallel during an upgrade" | The data has one sequence of transactions and the migration is one of them. There is no period in which the old and new versions both accept actions on the same data: each action applies to the schema in force at its place in the sequence, so nothing written on the old version needs to be caught up with. The upgrade is hot because it is a single transaction between actions, with no stop of the system. The kept snapshots of earlier program versions serve what still needs them: reading history under the program it was written in (MIG-7), and the migration transform itself. |
| J427516 | L427516 "If the API is unchanged or is compatible (all used components are unchanged) then the client can continue using it. A client that uses a changed or removed component is rejected and must reconnect against the new API. |
| J427517 | L427516 "a developer can version their APIs and maintain the old APIs against the new data zone as well as expose a new API" | A data zone can expose several APIs at once (API-1), so an old API can be kept, redefined over the new version's data, next to a new one; API versioning needs no feature of its own. |
| J427518 | L427516 "for as long as there exists a dataset that uses the old schema that you might want to migrate", "only the computation functions need to be preserved" | One program can have several datasets (e.g. separate deployments), each at its own program version, and any of them may later be migrated. For an old version, what is kept is its computation functions: with the stored data, which carries its own structure, they are enough to evaluate the old version's computed values, which the migration transform can read (MIG-5). The old version's actions, constraints and APIs need not be kept. Old versions are kept as long as some dataset that may still be migrated uses them. |
| J427529 | L427529 "actions whose data dependencies don't touch values from the previous action can actually run in parallel … without breaking atomicity", "new value prediction with a rollback" | The optimiser may run actions concurrently or speculatively only where the outcome is the same as running them one at a time in the single sequence of transactions (MIG-6): every result, version and constraint check is as if serial. A wrong speculation is rolled back before anything depending on it becomes visible. |
| J427530 | L427529 "I'd like to make it so that Upshot can still have the best hand tuned performance, in theory. | J428000 | L428000 "constraint relaxation annotation on the Upshot feature program" | A relaxation annotation is written in the feature language, on the element whose promise it relaxes (a read, a computed value, an action, a constraint, an API), and widens what results are acceptable there (e.g. a bounded-stale read, a tolerance, an order that is only rough). The optimiser may then use any acceptable result but is never required to; with no annotation the strict promise holds. This keeps OPT-2: the optimisation metadata still never changes results beyond what the program accepts. |
| J428001 | L428000 "actions are kinda like computation functions temporarily connected to the source values they modify. They can use the same structures and annotations" | An action is written with the same means as a computation function: the same expression language, the same structures (including computed collections and their identities) and the same annotations (relaxations included). It differs in direction and duration: a computation function's value stays connected to the sources it reads; an action's result is connected, for the length of one transaction, to the sources it writes. How to reconcile the two directions is open. |
| J428060 | L428060 "both ways of writing each function should be allowed for both usages" | Two forms of writing, each available for actions and for computed values: the **sequential** form (a sequence of operations, some of which write to targets) and the **per-target** form (one definition for each target's value, possibly through a helper that computes several values as a tuple, each target taking its entry). An action in the per-target form defines the value of every target it writes; a computed value in the sequential form is a function that writes several computed outputs. Both forms mean the same thing: a function from what it reads to the values of its targets. |
| J428306 | L428306 "In a same transaction a computed value cannot have a runtime circular dependency" | A run-time circular dependency is one that an actual evaluation follows: computing a value requires, through the values it reads in this evaluation, the value itself at the same version. It is a failure of the evaluation (ACT-4), never resolved by iterating to a fixed point. Dependencies across transactions are not cycles: an action reading the version before it and writing the next is allowed. |
| J428307 | L428306 "allow static time circular dependencies but have it require explicit annotation to bypass the error" | A static circular dependency is a cycle in the program's dependency graph that no evaluation need follow: dependencies chosen by a condition (Claude's A/B/flag example), or recursion over the data's structure (a directory's size from its subdirectories' sizes, acyclic as long as the data is). Without an annotation it is a compile-time error; with an explicit annotation on the values involved it is allowed, and the rule of J428306 still applies to each evaluation. |
| J428317 | L428317 "A transaction that triggers a cyclic dependency fails and triggers a rollback" | A run-time cycle is treated like a broken constraint (CONS-2): the action whose changes would give some computed value a circular dependency fails as a whole, none of its changes take effect, and the dataset never holds a version in which a computed value is circular. This holds whether or not anything reads that value, so the check happens when the action's changes are propagated, not when the value is first read. The failure can be handled like any other (ACT-4), by a handler running as a separate action. |
| J428329 | L428329 "An action could come with annotation specifying a subset of data values of interest and only validate the hot path along these data values" | The values of interest are the values the annotated action declares it cares about (e.g. what it reads and what its caller will read next). If a check on that path fails, the action fails and is rolled back as usual (CONS-2, MODEL-10). |
