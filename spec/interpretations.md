# Interpretations

Claude's interpretations of the user's messages (the log, `spec/log/`), kept apart from them; the user may
overrule them. Each row is `| J<id> | <sources> | <interpretation> |`; the sources column names the ids the row
reads. This file is append-only: rows are never renumbered, and new rows take their id from `tooling/up spec-id J`
(see [`README.md`](README.md)).

| # | Source | Interpretation |
|---|---|---|
| J426444 | L426443 "targets native interface integration. (C/C++)" | Upshot works with C and C++ code through their native interfaces (the C ABI and C/C++ headers), so programs and libraries written in C or C++ can use it and be used by it; the exact mechanism (generated bindings, headers, a runtime library) is a plan decision still to make. |
| J426464 | L426464 "the feature language" | Upshot has two parts: the **feature language**, in which a program and its data structures are written, and the **optimisation metadata**, kept apart from the program. The feature language is the Upshot language proper; L426443's "language" is this one. |
| J426465 | L426464 "optional metadata kept separately", "optimisation metadata is responsible for deciding which form … is persisted" | The optimisation metadata decides how the data is physically held (which values are stored and which recomputed, in memory and/or in a database, layouts and indexes); it changes performance, never results: what a program computes is defined by the feature language alone. Since it is optional, a program with no metadata still runs correctly under a default strategy. |
| J426466 | L426464 "some data as data sources and all others as computed" | A data source holds data as given (written by actions, not derived from other data); computed data is defined by an expression over other data and is always consistent with it. Every piece of data is exactly one of the two. |
| J426467 | L426464 "Some computed values can be bidirectional" | A bidirectional computed value has a two-way path to its sources: its sources determine it and it determines its sources, so either side can be the persisted form and the other derived; writing to it is carried back to its sources. |
| J426468 | L426464 "values that become connected to data sources … or to computed data with a two way computed path to data sources" | An action's results are written only to data sources, or to bidirectional computed values that carry the write back to their sources; an action never writes a one-way computed value. The user describes this as their current view ("I currently see"), so the action model is provisional. |
| J426469 | L426464 "all data is versioned" | Every change to data (source or computed) produces a new version, and a reader can tell which version of a value it sees. Whether and how long earlier versions stay readable is not yet specified. |
| J426470 | L426464 "the dataset can self inspect things like data being recomputed and the latest not being available yet" | A program can query, in the feature language, the state of its own data as data: e.g. that a computed value is being recomputed, or that the value it reads is not the latest version because the latest is not available yet. "Ideally" makes this a goal rather than a hard requirement. |
| J426531 | L426531 "Exposed values can be exposed as read/write" | An exposed value is read-only unless exposed as read/write. A write through an API follows the action rules (ACT-2): a read/write exposed value is a data source or a bidirectional computed value; a one-way computed value can only be exposed read-only. |
| J426532 | L426531 "data zones … can only interact via each other's API s" | Every piece of data belongs to exactly one data zone, and each API belongs to a zone. Code in one zone reads, writes and acts on another zone's data only through that zone's APIs: no direct references from one zone's data into another's. |
| J426533 | L426531 "As a matter of configuration/part of the optimisation language", L426464 "optimisation metadata" | The "optimisation language" is the form the optimisation metadata (OPT-1) is written in, and the assignment of zones to runtimes is part of it: like the rest of the metadata, it decides where and how data is held and run, not what the program computes (J426465). |
| J426534 | L426531 "ultimately a variety of runtimes could exist including on the cloud as web APIs", L426443 "There is no Azure/cloud/website for the project" | Not a contradiction: L426443 is about the project's own infrastructure and instructions (no Azure, cloud or website to build or run for this repository). A runtime that serves a zone as a web API in the cloud is a possible future product of Upshot, not infrastructure of this project, and is out of scope for now. |
