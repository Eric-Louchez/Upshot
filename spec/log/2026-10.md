### L426464 · 2026-10-24 · what Upshot is about: a feature language with sources, computed values and actions, optimisation metadata kept separately, versioned data (specification)

Context: answers the open question in `plan/README.md` on what "data-driven aspects of development" (L426443) covers.

```text
Here is what I want upshot to be about: today when managing data you can do it in memory and/or in a database. You must then architect your datastructures carefully and efficiently. This interferes with maintainability and feature velocity. Instead you define your datastructures in a way that optimizes maintenance and feature development. And provide the optimization structure as optional metadata kept separately. That metadata can be generated by hand, by code from usage metrics or by LLM.

So the feature language let's you specify your program using more intuitive datastructures that can include circular references, collections, collection references, etc... Things that are typically not possible in a database. The feature language also let's you specify computed values like counts, averages or even arbitrary computed values. Including computed collections. 

The feature language specifies some data as data sources and all others as computed. Some computed values can be bidirectional. The optimisation metadata is responsible for deciding which form would then be the one that is persisted. 

Next are actions. You can act on the data. I currently see an action as a data transformation of the inputs and the current dataset towards values that become connected to data sources of the data set or to computed data with a two way computed path to data sources. 

Additionally, all data is versioned. And ideally the dataset can self inspect things like data being recomputed and the latest not being available yet.
```

```text
The feature language also lets you define data zones. These are seperate areas where different zones can only interact via each other's API s.
```

### L427008 · 2026-10-24 · answers on the Tar Pit points: constraints reject actions, migrations needed, conversion between computed and source, sources still declared, history and observers open, the feature language never references the optimisation language, atomic actions, metadata per deployment (specification + questions)

Then smaller points: 1 observers (deltas, throttling, coalescing, observing expressions and history); 2 atomic multi-value updates, i.e. atomic actions; 3 several metadata sets for one program, one per runtime or deployment.

```text

2: Very good point. We will need an integrated migration story. What does the Tar Pit paper say on that topic?

3: Yeah, there's a design choice to be done here.  First, any computed value can be converted fairly easily into a source value. In principle any source value can also be converted to a computed value. These are things actions can do.  The "anything writable that is not two way is a source" is an insight about someone trying to design something and not understanding what they've built. For us: computed values that aren't two way all the way back to all sources are not writable. But any computed value can be converted to a source value and disconnected from its computed sources.

Smaller points

2: Correct, in my previous implementation attempt, actions are atomic but then there's the issue of being able to update source values, partially propagate computed values and continuing applying the action based on those computed values. ### L427076 · 2026-10-24 · exception handling for failed functions; APIs with mandatory source values provided by the runtime or harness (the current user); Upshot does not replace general-purpose languages (specification)
```

Context: Claude asked the user to confirm its reading that a rejected action leaves no trace: none of its changes take effect and no new version is produced (J427008).

```text
"Rejected actions leave no trace" ->  Functions may contain exception handling where a failed function triggers an exception handling function.

Then there's the practical question of how to handle a user within an API. E.g. what is the prescriptive way to structure a web backend data zone and that data zone's API. In a sense we want to present a slice of that data zone as dat API with the "current user' being some kind of built-in property value upon which the rest of the API exposed data pivots. 

Now, Upshot does not intend to be a complete replacement of today's programming languages. Certain things like the authentication/authorization layers of a web app might not be all that suited for Upshot.
```
