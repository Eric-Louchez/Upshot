### L426464 · 2026-10-24 · what Upshot is about: a feature language with sources, computed values and actions, optimisation metadata kept separately, versioned data (specification)

Context: answers the open question in `plan/README.md` on what "data-driven aspects of development" (L426443) covers.

```text
Here is what I want upshot to be about: today when managing data you can do it in memory and/or in a database. You must then architect your datastructures carefully and efficiently. This interferes with maintainability and feature velocity. Instead you define your datastructures in a way that optimizes maintenance and feature development. And provide the optimization structure as optional metadata kept separately. That metadata can be generated by hand, by code from usage metrics or by LLM.

So the feature language let's you specify your program using more intuitive datastructures that can include circular references, collections, collection references, etc... Things that are typically not possible in a database. The feature language also let's you specify computed values like counts, averages or even arbitrary computed values. Including computed collections. 

The feature language specifies some data as data sources and all others as computed. Some computed values can be bidirectional. The optimisation metadata is responsible for deciding which form would then be the one that is persisted. 

Next are actions. You can act on the data. I currently see an action as a data transformation of the inputs and the current dataset towards values that become connected to data sources of the data set or to computed data with a two way computed path to data sources. 

Additionally, all data is versioned. And ideally the dataset can self inspect things like data being recomputed and the latest not being available yet.
```

### L427445 · 2026-10-24 · migrations: parallel program versions kept as snapshots, a migration transform from old zones to the new zones' sources, automatic for matching structure, run as an action, history not rewritten, hot upgrades (specification)

Context: answers the open questions of the migration design study (`plan/migration.md` §5), among them when a migration runs (atomically at deployment or online), whether history spans program changes, what happens to the history of computed values, and whether a declared migration is a function or a lens.

```text
With metaprogramming, a migration is simply a metaprogramming operation.

Without migration, migration becomes a built-in metaprogramming-like operation.

Actually come to think of it, we should implement the much needed parallel code versions in a single program while migrations are allowed. Basically you must keep a snapshot of your whole program at each migration version you want to support. Then you also write a migration transform from the old program to the new program. Which in our case means migrating from the old data zone(s) to the source values of the new data zones. 

What we might want to do here is automatic migrations for source data in the new version where the matching value in the old version has the same format/data type/structure. Even if the old value is a computed value.

The migration operation is treated like a normal action which has its own transaction version.

The version history is not rewritten. But some values may end up not existing anymore (as identified by their instance ID and there may be new values that don't have version histories from before the migration. But none of that is new to the system. Overall this seems to offer good flexibility and usability. While also enabling hot upgrades with no downtime.
```
